## JWT Token Validation Flow

### Token Generation
```
Frontend POST /user/register or /user/login
  ↓
Backend (BE-Project or Cloud-Backend)
  ↓
Backend signs with: jwt.sign(payload, JWT_SECRET)
  ↓
Returns token to Frontend
  ↓
Frontend stores in localStorage as 'authToken'
```

### Token Verification
```
Frontend sends request with: Authorization: Bearer {token}
  ↓
Backend receives request
  ↓
Backend verifies with: jwt.verify(token, JWT_SECRET)
  ↓
✅ If JWT_SECRET matches: User authenticated
❌ If JWT_SECRET differs: Verification fails (401)
```

## Critical Integration Points

### 1️⃣ JWT_SECRET Must Match
**Requirement**: Both BE-Project and Cloud-Backend must use SAME JWT_SECRET

✅ **Current Status**:

- Cloud-Backend EC2: `JWT_SECRET=qwertyuiop1234567890`

**Why It Matters**:
- If user logs into BE-Project, gets token signed with secret `A`
- But cloud-backend verifies with secret `B`
- Verification fails → 401 Unauthorized
- This breaks cross-service authentication

### 2️⃣ CORS Configuration
**Requirement**: Both backends must allow requests from frontend

**Current Status**:
```
BE-Project .env:
  CORS_ORIGIN=http://localhost:3000,http://localhost:8000
  ✅ Allows frontend on port 8000

Cloud-Backend .env.example:
  CORS_ORIGIN=http://localhost:8080
  (Should be updated for EC2 production)
```

**For EC2 Production**:
```
CORS_ORIGIN=https://yourdomain.com,https://www.yourdomain.com
```

### 3️⃣ Token Field Normalization
Both backends normalize JWT payload fields for compatibility:

```javascript
// Token can contain:
{
  user_id: "uuid",      // PostgreSQL snake_case
  userId: "uuid",       // JavaScript camelCase
  userID: "uuid",       // Alternate camelCase
  username: "user",     // Snake case variant
  userName: "user",     // Camel case variant
  email: "user@example.com"
}

// Both backends normalize these variations
// So tokens work regardless of naming convention
```

This allows tokens generated by either service to work everywhere.
